# M18. Безопасность пользовательского ввода.

Учебный разбор, подготовленный по теме силабуса.

По силабусу: Недоверенные входные данные, проверка значений и экранирование вывода. Параметризованные SQL-запросы. Анализ типовых ошибок обработки форм и разграничение данных и исполняемого кода.

## Разные границы — разные меры

Валидация проверяет допустимость значений. Экранирование HTML не даёт данным стать разметкой в нужном контексте. Подготовленный SQL-запрос отделяет значения от команды. Проверка доступа решает, разрешено ли действие этому пользователю. Одна мера не заменяет остальные.

## XSS, SQL-инъекция и CSRF

XSS возникает, когда данные становятся исполняемой частью страницы. Для текстовых узлов используй textContent, в PHP — корректное HTML-экранирование. SQL-параметры передавай отдельно. Для изменения состояния с cookie-аутентификацией нужны серверная проверка CSRF-токена и другие подходящие меры.

## AJAX и JSON

fetch не отклоняет Promise только из-за статуса 404: проверяй response.ok. JSON разбирают штатным парсером, не eval. CORS определяет доступ браузерного кода к ответу другого origin; это не проверка прав на сервере. CAPTCHA дополняет защиту от автоматизации, но не гарантирует её.

## Пример

```javascript
async function loadUsers() {
  const response = await fetch("./examples/users.json");
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  const users = await response.json();
  if (!Array.isArray(users)) throw new Error("Ожидался массив");
  return users.map(user => String(user.name ?? "Без имени"));
}
// Для вывода: создайте элемент и присвойте ему textContent.
loadUsers().then(console.log).catch(console.error);
```

На размещённом сайте или локальном HTTP-сервере запрос вернёт имена из examples/users.json. Через file:// запрос может блокироваться.

Обрати внимание: Не вставляй внешний err.message через innerHTML. Ошибки тоже выводи как текст.
